## Cross-Phase Integration Findings

### ✗ Critical Gap 1: OBJ-02 — Launch-from-objective flow broken at UI layer

**Phase link:** Phase 16 (backend) → Phase 17 (UI)

The backend correctly accepts `objectiveId` on `POST /executions` and the objective detail page's run history table queries `GET /objectives/:id/executions` which joins on the FK. But:

- `services/ui/src/lib/api.ts` `createExecution()` body interface has no `objectiveId` field
- `services/ui/src/routes/new-execution/+page.server.ts` never extracts or forwards `objectiveId`
- `/objectives/[id]/+page.svelte` has no "Launch from objective" button

**Consequence:** All executions created from the UI have `objectiveId = null`. The objective hub run history table is permanently empty for any user who creates executions through the UI. This negates the core value proposition of the named objectives feature.

---

### ✗ Critical Gap 2: BOT-04 — Spawn-timeout error state overwritten

**Phase link:** Phase 15-02 `startSpawnTimeoutChecker` → Phase 15-03 UI error surfacing

`startSpawnTimeoutChecker` correctly writes `status='failed'` and `errorMessage` to the DB at line 375-380, then calls `await stopBot(entry.botId, 'failed')`. The `stopBot` function unconditionally writes `{ status: 'stopped' }`, overwriting the error state before the UI can read it.

Plan 15-04 (gap_closure: true) was designed to fix this with a `skipDbUpdate` option on `stopBot`, but was never executed. `grep skipDbUpdate` returns zero matches in `bot-orchestrator.ts`.

**Consequence:** Users with bots that time out during spawn see the bot as "stopped" with no error message instead of "failed" with a human-readable timeout reason.
