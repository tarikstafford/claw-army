**src/services/execution.service.ts:**

Create the execution service module with three exported functions:

1. `createExecution(input)` — Inserts a new row into the `executions` table using Drizzle. Input fields: `objective` (string), `maxBots` (number), `budgetCapCents` (number), `runtimeLimitSeconds` (number), `allowedTools` (string[]). Status defaults to `'queued'`. Returns `{ executionId: string; status: 'queued' }`. Use `.returning({ id: executions.id })` and check `result.length` before accessing `result[0]` (per noUncheckedIndexedAccess in tsconfig.base.json).

2. `getExecution(id)` — Selects a single execution by UUID. Returns the full execution row or `null` if not found. Use `db.select().from(executions).where(eq(executions.id, id))`.

3. `transitionExecution(executionId, fromStatus, toStatus)` — Atomic state transition using `db.update(executions).set({ status: toStatus, updatedAt: new Date() }).where(and(eq(executions.id, executionId), eq(executions.status, fromStatus))).returning({ id: executions.id })`. Returns `boolean` — true if transition succeeded (result.length === 1), false if the row was not in the expected state (race condition or invalid transition). The `fromStatus` and `toStatus` parameters should be typed using the execution status enum values from the schema.

Import `db` and `executions` from `@claw/db`. Import `eq`, `and` from `drizzle-orm`.

**Valid state transitions (for reference — enforce in Phase 3 via a state map, not in Phase 2):**
- queued -> running
- running -> paused | completed | failed | stopped
- paused -> running | stopped
- stopped -> (terminal)
- completed -> (terminal)
- failed -> (terminal)

For Phase 2, `transitionExecution` does NOT validate the transition path — it only ensures atomic WHERE-clause guarding. Transition validation is a Phase 3 enhancement.
