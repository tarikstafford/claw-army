Create `services/execution-service/src/events/guardrail-watchdog.ts` — a setInterval-based polling module that detects guardrail violations and revokes offending bots.

**Imports:**
- `IORedis` from `ioredis`
- `db`, `bots`, `toolInvocations` from `@claw/db`
- `eq`, `and`, `desc`, `inArray` from `drizzle-orm`
- `publishGuardrailTriggered` from `./publisher` (added in 04-01)
- `stopBot` from `../orchestrator/bot-orchestrator`
- `botRegistry` from `../orchestrator/bot-registry`

**Constants (env-var configurable):**
```typescript
const WATCHDOG_INTERVAL_MS = Number(process.env.WATCHDOG_INTERVAL_MS ?? 10_000);
const LOOP_DETECTION_WINDOW = Number(process.env.LOOP_DETECTION_WINDOW ?? 5); // N identical consecutive calls
const GUARDRAIL_DENY_TTL_SECONDS = Number(process.env.GUARDRAIL_DENY_TTL_SECONDS ?? 3600);
```

**Redis client:**
Create a module-level IORedis instance from `process.env.REDIS_URL ?? 'redis://localhost:6379'`. This reads rate-limiter keys (written by tool-gateway's rate-limiter-flexible) and writes deny-list keys.

**Core function: `revokeBot(botId, executionId, reason)`**
1. Set Redis deny-list key: `redis.setex('guardrail:denied:${botId}', GUARDRAIL_DENY_TTL_SECONDS, '1')`
2. Call `stopBot(botId, 'terminated')` to stop the container and update Postgres
3. Call `publishGuardrailTriggered()` with a complete event payload:
   ```typescript
   {
     type: 'guardrail_triggered',
     botId,
     executionId,
     reason,
     action: 'revoked',
     timestamp: new Date().toISOString(),
   }
   ```
4. Wrap the entire function in try/catch — log errors but never throw (watchdog must survive)

**Rate violation detection: `checkRateViolations()`**
For each active bot in `botRegistry`:
1. Read the rate-limiter-flexible Redis key for call rate: `redis.get('rl:calls:${botId}')`. The key stores a JSON object with `points` consumed. If `points >= 60` (the limit from rate-limit.ts), the bot has exceeded its call rate.
2. Read the token rate key: `redis.get('rl:tokens:${botId}')`. If `points >= 100000`, the bot has exceeded its token rate.
3. If either limit is exceeded AND the bot is NOT already in the deny-list (`redis.get('guardrail:denied:${botId}')` returns null), call `revokeBot(botId, executionId, 'rate_limit')`.

**IMPORTANT NOTE on rate-limiter-flexible key format:** The `RateLimiterRedis` stores its state in a key like `rl:calls:{botId}` as a Redis string containing the consumed points count. However, the internal format may vary by version. The safest approach is: instead of reading rate-limiter keys directly, query `tool_invocations` to count invocations in the last 60 seconds per bot. This is more reliable than depending on rate-limiter-flexible's internal key structure.

**Revised approach for rate violation detection:**
For each active bot in `botRegistry`:
1. Query `SELECT COUNT(*) FROM tool_invocations WHERE bot_id = $botId AND invoked_at > NOW() - INTERVAL '60 seconds'`. If count >= 60 (call rate limit), flag as rate violation.
2. Query `SELECT COALESCE(SUM(total_tokens), 0) FROM tool_invocations WHERE bot_id = $botId AND invoked_at > NOW() - INTERVAL '60 seconds'`. If sum >= 100000 (token rate limit), flag as rate violation.
3. If flagged AND not already denied, call `revokeBot(botId, executionId, 'rate_limit')`.

Use Drizzle for these queries (already imported). Use `sql` template literal for the interval arithmetic:
```typescript
import { sql } from 'drizzle-orm';

const cutoff = new Date(Date.now() - 60_000);
const [row] = await db
  .select({ count: sql<number>`count(*)` })
  .from(toolInvocations)
  .where(and(eq(toolInvocations.botId, botId), sql`${toolInvocations.invokedAt} > ${cutoff}`));
```

**Loop detection: `checkLoopBehavior()`**
For each active bot in `botRegistry`:
1. Query the last N (`LOOP_DETECTION_WINDOW`) tool invocations:
   ```typescript
   const recent = await db
     .select({
       toolName: toolInvocations.toolName,
       requestSummary: toolInvocations.requestSummary,
     })
     .from(toolInvocations)
     .where(eq(toolInvocations.botId, botId))
     .orderBy(desc(toolInvocations.invokedAt))
     .limit(LOOP_DETECTION_WINDOW);
   ```
2. If `recent.length < LOOP_DETECTION_WINDOW`, skip (not enough data).
3. Compare all entries: create a fingerprint for each as `JSON.stringify({ toolName, args: requestSummary })`. If ALL fingerprints are identical, it's a loop.
4. If loop detected AND not already denied, call `revokeBot(botId, executionId, 'loop_detected')`.

**Watchdog lifecycle:**
```typescript
export function startGuardrailWatchdog(): NodeJS.Timeout {
  console.log('[guardrail-watchdog] Starting with interval', WATCHDOG_INTERVAL_MS, 'ms');
  return setInterval(async () => {
    try {
      await checkRateViolations();
      await checkLoopBehavior();
    } catch (err) {
      console.error('[guardrail-watchdog] Polling error (non-fatal):', err);
    }
  }, WATCHDOG_INTERVAL_MS);
}

export function stopGuardrailWatchdog(timer: NodeJS.Timeout): void {
  clearInterval(timer);
}
```

Add a Redis deny-list check to the Tool Gateway's `/tool.invoke` handler. This is the enforcement point — when the Guardrail Watchdog adds a bot to the deny-list, the Tool Gateway immediately blocks all subsequent requests from that bot.

**Add Redis import at the top of tool-invoke.ts:**
```typescript
import IORedis from 'ioredis';

const redis = new IORedis(process.env.REDIS_URL ?? 'redis://localhost:6379');
```

Note: This is a separate IORedis instance from the rate-limiter's connection. It uses default settings (not `enableOfflineQueue: false`). This is acceptable because the deny-list check is a simple GET — if Redis is down, fail-open (same pattern as rate-limit.ts).

**Add deny-list check as the FIRST enforcement gate in the handler,** immediately after the required-fields check (`if (!toolName || !botId || ...)`) and BEFORE the allowlist check:

```typescript
// 0. Bot deny-list check (GARD-02, GARD-03, GARD-04)
// If the Guardrail Watchdog has revoked this bot, reject immediately.
try {
  const isDenied = await redis.get(`guardrail:denied:${botId}`);
  if (isDenied) {
    await writeAuditLog({
      executionId,
      botId,
      toolName,
      invocationId,
      rejected: true,
      rejectionReason: 'bot_revoked',
      requestSummary: { toolName, args },
    });
    return reply.status(403).send({
      success: false,
      error: 'Bot has been revoked by guardrail watchdog',
    });
  }
} catch (err) {
  // Fail-open: if Redis is unavailable, allow the request
  // (same pattern as rate-limit.ts fail-open behavior)
  console.error('[tool-invoke] Redis error in deny-list check (fail-open):', err);
}
```

The deny-list check:
- Returns 403 (not 429) because the bot is permanently revoked, not temporarily rate-limited
- Writes an audit log entry with `rejectionReason: 'bot_revoked'` for traceability
- Fails open on Redis errors to avoid blocking legitimate bots during transient Redis issues
- Runs BEFORE the allowlist check (step 1) because deny-list is the highest priority security gate

**Do NOT:**
- Change the existing rate limit, allowlist, or Zod validation logic — they remain unchanged
- Use SISMEMBER (set-based) — the deny-list uses per-key SETEX for automatic TTL expiration, not a set
- Block on Redis errors — fail-open, same pattern as existing rate-limit middleware
