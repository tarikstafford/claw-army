**Problem (Pitfall 2 — CRITICAL):** Both Akasa and Paperclip use `drizzle.__drizzle_migrations` as their migration journal table. Running both against the same Postgres database will corrupt each other's journal.

**Fix:** Add `migrations` config to `packages/db/drizzle.config.ts` to use a separate table name `__akasa_migrations` in the `drizzle` schema.

Replace `packages/db/drizzle.config.ts` with:
```typescript
import 'dotenv/config';
import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  out: './migrations',
  schema: './src/schema/**/*.ts',
  dialect: 'postgresql',
  dbCredentials: {
    url: process.env['DATABASE_URL']!,
  },
  migrations: {
    table: '__akasa_migrations',
    schema: 'drizzle',
  },
});
```

The only change is adding the `migrations` block with `table: '__akasa_migrations'` and `schema: 'drizzle'`. This ensures:
- Akasa writes migration records to `drizzle.__akasa_migrations`
- Paperclip continues using `drizzle.__drizzle_migrations`
- Both run independently with zero journal collision

**Note:** Existing Akasa migrations that were already applied using the old default table (`__drizzle_migrations`) will NOT be recognized by the new table. On a fresh database this is irrelevant. On an existing database, developers may need to copy rows from `drizzle.__drizzle_migrations` to `drizzle.__akasa_migrations` — but since this is a v6.0 foundation reset, a fresh database is expected.
