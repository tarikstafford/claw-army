**src/services/planner.service.ts:**

Create a deterministic stub planner. No LLM calls — this is Phase 2 only.

```typescript
export interface PlannedTask {
  description: string;
}

/**
 * Stub planner: decomposes objective into N parallel tasks.
 * Phase 3 replaces this with real LLM decomposition.
 *
 * Strategy: Split objective into maxTasks independent subtasks.
 * Each task gets a numbered description derived from the objective.
 */
export function planObjective(objective: string, maxTasks = 3): PlannedTask[] {
  const trimmed = objective.trim();
  return Array.from({ length: maxTasks }, (_, i) => ({
    description: `${trimmed} (subtask ${i + 1} of ${maxTasks})`,
  }));
}
```

The planner takes the objective string and a task count. It returns N `PlannedTask` objects with numbered descriptions. This is intentionally simple — the goal is to produce N tasks for bot consumption, not to do intelligent decomposition.

**src/queue/task-queue.ts:**

Create the BullMQ task queue module with SEPARATE ioredis connections for Queue and Worker (per RESEARCH.md Pitfall 1).

```typescript
import { Queue, Worker, type Job } from 'bullmq';
import IORedis from 'ioredis';
```

**Key constants:**
- `TASK_QUEUE_NAME = 'claw-tasks'`
- `LOCK_DURATION_MS = 30_000` (30 seconds — bot must complete or have lock renewed within this window)
- `STALLED_INTERVAL_MS = 15_000` (check for stalled jobs every 15 seconds)
- `MAX_STALLED_COUNT = 2` (allow 2 stalls before marking job as permanently failed)

**Exports:**

1. `queueConnection` — `new IORedis(REDIS_URL)` where `REDIS_URL = process.env.REDIS_URL ?? 'redis://localhost:6379'`. Default maxRetriesPerRequest (fast-fail for producers).

2. `workerConnection` — `new IORedis(REDIS_URL, { maxRetriesPerRequest: null })`. CRITICAL: Workers need infinite retry for blocking commands (BRPOPLPUSH). Without `maxRetriesPerRequest: null`, the worker silently stops processing after Redis reconnection.

3. `TaskJobData` interface — `{ taskId: string; executionId: string; description: string }`

4. `taskQueue` — `new Queue<TaskJobData>(TASK_QUEUE_NAME, { connection: queueConnection })`. This is the producer-side queue. Used by the planner to add task jobs.

5. `createTaskWorker(processor)` — Factory function that creates a BullMQ Worker:
   - Takes a `processor: (job: Job<TaskJobData>) => Promise<string>` callback
   - Creates `new Worker<TaskJobData, string>(TASK_QUEUE_NAME, processor, { connection: workerConnection, lockDuration: LOCK_DURATION_MS, stalledInterval: STALLED_INTERVAL_MS, maxStalledCount: MAX_STALLED_COUNT, concurrency: 1 })`
   - CRITICAL: Attaches `worker.on('error', (err) => console.error('[TaskWorker] Error:', err))` immediately. Without this handler, worker errors are swallowed silently.
   - Returns the worker instance.

6. `addTaskToQueue(data: TaskJobData)` — Convenience wrapper that calls `taskQueue.add('task', data, { attempts: 3, backoff: { type: 'exponential', delay: 1000 } })`. Returns the job.

**Dual-write strategy (documented in code comment):** Per RESEARCH.md Open Question 2, the recommended approach is: write to Postgres first (create task row), then add to BullMQ queue. If BullMQ fails, the task stays 'pending' in Postgres — a reconciler can re-enqueue later. This avoids orphan queue jobs with no DB record.

```typescript
// Trigger async planning after returning 201 (non-blocking)
setImmediate(async () => {
  try {
    // 1. Plan tasks (stub — no LLM)
    const plannedTasks = planObjective(objective, maxBots);

    // 2. Dual-write: Postgres first, then BullMQ
    for (const planned of plannedTasks) {
      // Write to Postgres (create task row with status 'pending')
      const result = await db
        .insert(tasks)
        .values({
          executionId,
          description: planned.description,
          status: 'pending',
        })
        .returning({ id: tasks.id });

      if (result.length > 0) {
        const taskRow = result[0]!;
        // Write to BullMQ queue
        await addTaskToQueue({
          taskId: taskRow.id,
          executionId,
          description: planned.description,
        });
      }
    }

    // 3. Transition execution to 'running'
    await transitionExecution(executionId, 'queued', 'running');

    fastify.log.info({ executionId, taskCount: plannedTasks.length }, 'Planning complete, execution running');
  } catch (err) {
    fastify.log.error({ err, executionId }, 'Failed to plan and queue tasks');
    // Transition to failed on planning error
    await transitionExecution(executionId, 'queued', 'failed').catch(() => {});
  }
});
```

**Imports to add:**

The key design points:
1. `setImmediate` ensures POST returns 201 within the 1-second SLA (success criteria #1)
2. Postgres-first dual-write: task row created before BullMQ add (per RESEARCH.md recommendation)
3. Execution transitions queued -> running after all tasks are queued
4. try/catch with `fastify.log.error` prevents silent failure (per RESEARCH.md Open Question 5)
5. On planning failure, transition to 'failed' state
