**Step 1: Create services/tool-gateway/Dockerfile.**

Follow the pattern from `services/stub-bot/Dockerfile` and `services/bot-worker/Dockerfile`:

```dockerfile
FROM node:20-alpine AS base

WORKDIR /app

# Copy workspace root for pnpm
COPY package.json pnpm-workspace.yaml pnpm-lock.yaml ./
COPY .npmrc ./

# Copy package manifests for all workspace deps
COPY packages/db/package.json packages/db/
COPY packages/shared-types/package.json packages/shared-types/
COPY packages/event-schemas/package.json packages/event-schemas/
COPY packages/tool-contracts/package.json packages/tool-contracts/
COPY services/tool-gateway/package.json services/tool-gateway/

# Install dependencies
RUN corepack enable && corepack prepare pnpm@latest --activate
RUN pnpm install --frozen-lockfile --filter @claw/tool-gateway...

# Copy source
COPY packages/db/ packages/db/
COPY packages/shared-types/ packages/shared-types/
COPY packages/event-schemas/ packages/event-schemas/
COPY packages/tool-contracts/ packages/tool-contracts/
COPY services/tool-gateway/ services/tool-gateway/

WORKDIR /app/services/tool-gateway

ENV NODE_OPTIONS="--conditions @claw/source"

EXPOSE 3002

CMD ["npx", "tsx", "src/main.ts"]
```

**CRITICAL:** The tool-gateway Dockerfile needs `packages/tool-contracts` in the COPY list (the gateway validates against these schemas). It also needs `packages/db` for audit log writes.

Build the image:
```bash
docker build -t claw-tool-gateway:latest -f services/tool-gateway/Dockerfile .
```

**Step 2: Recreate bot-internal network with --internal flag.**

The existing `bot-internal` network from Phase 2 was created WITHOUT `--internal`. The `--internal` flag prevents Docker from adding a default gateway route, blocking all external routing. This is a breaking change documented in research.

```bash
# Remove existing network (may fail if containers are attached — stop them first)
docker network rm bot-internal 2>/dev/null || true
# Recreate with --internal flag
docker network create --internal bot-internal
```

Document this in the test script and docker-compose comments.

**Step 3: Update docker-compose.dev.yml.**

Add the `tool-gateway` service to the existing docker-compose.dev.yml. The key configuration is DUAL network attachment:

```yaml
tool-gateway:
  build:
    context: .
    dockerfile: services/tool-gateway/Dockerfile
  container_name: tool-gateway
  ports:
    - "3002:3002"
  environment:
    - PORT=3002
    - BOT_JWT_SECRET=${BOT_JWT_SECRET:-claw-dev-secret-do-not-use-in-prod}
    - DATABASE_URL=postgresql://postgres:postgres@postgres:5432/claw
    - REDIS_URL=redis://redis:6379
    - ARTIFACT_ROOT=/artifacts
    - FETCH_URL_DOMAIN_ALLOWLIST=${FETCH_URL_DOMAIN_ALLOWLIST:-}
    - LOG_LEVEL=${LOG_LEVEL:-info}
  volumes:
    - claw-artifacts:/artifacts
  networks:
    - default        # external access (LLM APIs, database, Redis)
    - bot-internal   # receives requests from bot containers
  depends_on:
    - postgres
    - redis
```

Add the `bot-internal` network to the networks section:
```yaml
networks:
  default:
    driver: bridge
  bot-internal:
    driver: bridge
    internal: true   # <-- this is the docker-compose equivalent of --internal
```

Add the `claw-artifacts` volume:
```yaml
volumes:
  postgres-data:     # existing
  claw-artifacts:    # new — for write_file artifacts
```

Ensure existing bot container definitions (if any) are configured with ONLY `bot-internal` network:
```yaml
# Bot containers (spawned by execution-service via dockerode, not compose)
# are configured in bot-orchestrator.ts: NetworkMode: 'bot-internal'
```

**IMPORTANT:** The tool-gateway is on BOTH networks. Bot containers are ONLY on bot-internal. This is how the security boundary works: bots can reach the gateway (same network), but cannot reach the internet (internal network blocks external routing).

**Step 1: Create scripts/network-isolation-test.sh.**

This script validates Phase 3 Success Criterion #1: "A bot container attempting any outbound connection other than POST /tool.invoke on the Tool Gateway is blocked."

The script:
1. Ensures `bot-internal` network exists with `--internal` flag. Recreates if needed.
2. Ensures the tool-gateway container is running (via compose or manual docker run).
3. Starts a test bot container on the `bot-internal` network with `curl` and `nslookup` installed (use `node:20-alpine` with `apk add curl bind-tools`).
4. From the test bot container, runs:
   - **Test A: External HTTP blocked.** `curl --max-time 5 https://api.openai.com/v1/models` — must fail (timeout or connection refused). Exit code non-zero = PASS.
   - **Test B: DNS query blocked.** `nslookup api.openai.com` — must fail or timeout on `--internal` networks. Note: Docker embedded DNS may resolve names even on internal networks, but TCP connections are blocked. This test is informational per Phase 1 decision.
   - **Test C: Gateway reachable.** `curl -s http://tool-gateway:3002/health` — must return `{"status":"ok"}`. Exit code 0 = PASS.
5. Reports results. Exits 1 if Test A or Test C fails (Test B is informational).
6. Cleans up test container.

Make the script executable: `chmod +x scripts/network-isolation-test.sh`.

Follow the pattern from `infra/docker/egress-test.sh` (Phase 1): use readiness probes, clean up on exit.

**Step 2: Create services/execution-service/src/__tests__/phase3-e2e.test.ts.**

This is an integration test that verifies the Phase 3 success criteria that can be tested programmatically (criteria #2, #3, #4). Full end-to-end with real Docker containers is covered by the network-isolation-test.sh script (criterion #1) and manual verification (criterion #5 requires real LLM API keys).

The test uses vitest and directly calls the Tool Gateway's HTTP endpoint:

```typescript
import { describe, it, expect, beforeAll, afterAll } from 'vitest';
```

**Prerequisites:** Tool Gateway must be running locally (port 3002). Test creates a real execution row in the DB for allowlist testing.

**Setup:**
1. Create a test execution in the DB with `allowedTools: ['llm_call', 'write_file']` (fetch_url intentionally excluded for testing).
2. Mint a test JWT using `mintBotJwt` from execution-service (or jose directly with BOT_JWT_SECRET).
3. Create a bot row in the DB for the test execution.

**Test cases:**

- **SC#2 — Allowlist rejection:** POST /tool.invoke with toolName `fetch_url` (not in allowed_tools). Expect 403. Query tool_invocations table — expect a row with `rejected: true`, `rejectionReason: 'not_in_allowlist'`, correct `botId`, `toolName`, and `invokedAt` timestamp.

- **SC#3 — Schema validation rejection:** POST /tool.invoke with toolName `llm_call` but malformed args (e.g., `args: { model: 123 }` — model should be string). Expect 422. Response body should include Zod validation error details. Query tool_invocations — expect `rejected: true`, `rejectionReason: 'schema_validation_failed'`.

- **SC#4 — Rate limit enforcement:** In a loop, send 61 rapid-fire `write_file` invocations (calls limiter allows 60/min). The 61st call should return 429. Query tool_invocations — expect the 61st has `rejected: true`, `rejectionReason: 'rate_limit_exceeded'`. **Note:** This test modifies Redis rate limit state — reset the rate limit key before and after the test.

- **SC#5 — Tool dispatch (write_file only, no API key needed):** POST /tool.invoke with valid `write_file` request (toolName: 'write_file', args: { path: 'test-output.txt', content: 'hello world' }). Expect 200. Response should include `result.artifactId` (UUID) and `result.sizeBytes`. Query tool_invocations — expect `rejected: false`, `durationMs` populated.

**Test configuration notes:**
- Use `BOT_JWT_SECRET=test-secret` env var (same as gateway).
- Skip tests if gateway is not running (`fetch` to health endpoint fails → `describe.skip`).
- Use vitest `resolve.alias` for `@claw/*` packages (same pattern as Phase 2 E2E tests).
- Clean up: delete test execution, bot, and tool_invocations rows after tests.
