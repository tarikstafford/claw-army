```typescript
const redis = new IORedis(process.env.REDIS_URL ?? 'redis://localhost:6379');
```

Note: This is a module-level singleton, same pattern as the rate-limit.ts in tool-gateway. Do NOT use `enableOfflineQueue: false` here — execution creation is write-path and should queue if Redis is temporarily slow.

**In `createExecution()`, after the successful Postgres INSERT (after the `if (result.length === 0)` check), add:**

```typescript
// Initialize Redis budget cap key for atomic enforcement (GARD-01)
// The Billing Engine (04-03) uses a Lua script that reads this key atomically.
// TTL = runtimeLimitSeconds + 24h buffer (ensures key outlives execution)
const ttlSeconds = input.runtimeLimitSeconds + 86400;
await redis.setex(
  `budget:cap:${result[0].id}`,
  ttlSeconds,
  input.budgetCapCents.toString(),
);
// Initialize spend counter to 0 (INCRBY on non-existent key creates it as 0,
// but explicit SET ensures the key exists for monitoring)
await redis.setex(
  `budget:spend:${result[0].id}`,
  ttlSeconds,
  '0',
);
```

**Important:** Wrap the Redis calls in try/catch and log-only on failure — budget key initialization failure should NOT prevent execution creation. The billing engine will handle missing keys gracefully (no cap = allow all spending, per the Lua script design in research).

```typescript
try {

  // ...
} catch (err) {
  console.error('[execution.service] Failed to initialize budget cap in Redis (non-fatal):', err);
}
```

Do NOT modify `getExecution()` or `transitionExecution()` — they are unchanged.
