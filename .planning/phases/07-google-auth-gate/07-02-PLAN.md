  <name>Task 1: Create verify-auth-token.ts with HKDF + JWE decryption</name>
  <files>

  <action>
    Create the directory services/execution-service/src/lib/ if it does not exist.

    Create services/execution-service/src/lib/verify-auth-token.ts with the following implementation:

    Import compactDecrypt from 'jose' and crypto from 'node:crypto'.

    Export async function verifyAuthToken(authHeader: string | undefined): Promise<boolean>

    Implementation logic:
    1. If authHeader is undefined or does not start with 'Bearer ', return false.
    2. Extract the token by slicing off the 'Bearer ' prefix (7 chars). If token is empty string, return false.
    3. Read AUTH_SECRET from process.env.AUTH_SECRET. If not set, throw new Error('AUTH_SECRET not configured').
    4. Auth.js uses different cookie names (and therefore different HKDF salts) for HTTP vs HTTPS:
       - HTTP/dev: 'authjs.session-token'
       - HTTPS/prod: '__Secure-authjs.session-token'
       Try BOTH salts — whichever was used to issue the token must match what we try.
    5. For each salt in ['authjs.session-token', '__Secure-authjs.session-token']:
       a. Build the HKDF info string: `Auth.js Generated Encryption Key (${salt})`
       b. Derive a 64-byte (512-bit) key using crypto.hkdfSync('sha256', secret, salt, info, 64)
          - 'sha256' is the hash algorithm
          - secret is process.env.AUTH_SECRET (string — Node accepts string as keying material)
          - salt is the cookie name string
          - info is the string from step (a)
          - 64 is the key length in bytes (required for A256CBC-HS512)
       c. Wrap as Uint8Array: new Uint8Array(keyBuffer)
       d. Try: const { plaintext } = await compactDecrypt(token, key)
       e. Parse: const payload = JSON.parse(Buffer.from(plaintext).toString('utf8'))
       f. If payload has a truthy 'email' or 'sub' field, return true
       g. On any error in this try block, catch and continue to next salt
    6. If neither salt succeeds, return false.

    WHY jose compactDecrypt (not jwt.verify): Auth.js v5 stores sessions as JWE (JSON Web Encryption, A256CBC-HS512), not plain signed JWTs. compactDecrypt decrypts the encrypted token. jwt.verify only validates signatures on plain JWTs and would fail with a JWE.

    WHY try both salts: The cookie name is used as the HKDF salt. In dev (HTTP), the cookie is named 'authjs.session-token'. In prod (HTTPS), it's '__Secure-authjs.session-token'. The backend does not know which environment the UI is running in, so try both. The first successful decryption wins.

    WHY 64 bytes: A256CBC-HS512 requires a 512-bit (64-byte) key.

  <name>Task 2: Add preHandler auth check to POST /executions</name>
  <files>

  <action>
    Update services/execution-service/src/routes/executions.ts:

    1. Add import at top of file:
       import { verifyAuthToken } from '../lib/verify-auth-token.js';

    2. Find the existing `fastify.post('/', { schema: { ... } }, async (request, reply) => {` registration.

    3. Add a preHandler array to the route options object (the second argument to fastify.post):
       preHandler: [
         async (request, reply) => {
           const valid = await verifyAuthToken(request.headers.authorization);
           if (!valid) {
             return reply.code(401).send({ error: 'Unauthorized' });
           }
         },
       ],

    The final POST / registration structure should be:
       fastify.post('/', {
         schema: { /* existing schema unchanged */ },
         preHandler: [
           async (request, reply) => {
             const valid = await verifyAuthToken(request.headers.authorization);
             if (!valid) {
               return reply.code(401).send({ error: 'Unauthorized' });
             }
           },
         ],
       }, async (request, reply) => {
         /* existing handler completely unchanged */
       });

    Do NOT change the route handler, schema, or any other routes. Only the POST / route gets the preHandler. GET routes remain unprotected (they are read-only execution status data).

    WHY preHandler (not onRequest): preHandler fires after body parsing and content-type detection, but before the main handler. This is the correct Fastify lifecycle hook for auth guards that need to reject before business logic runs.

    WHY return reply.code(401) (not throw): Returning in a Fastify preHandler short-circuits execution and sends the response. The main handler does not execute.
